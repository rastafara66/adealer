# Автоматичні звіти про помилки

> Модель `adealer.error.report` + декоратор `report_errors`. Додано у `19.0.1.7.0`.
> За згодою, типово вимкнено.

## Навіщо

Дилер, у якого модуль зламався, майже ніколи не пише розробнику — він його
вимикає й іде далі. Без автозвіту про баг дізнаєшся з падіння продажів, а не з
повідомлення. Тому несподівані збої звітують про себе самі.

## Головне обмеження, з якого все випливає

Модуль торкається авто, клієнтів, замовлень і сум. У тексті помилки цілком
реально опиняться VIN, ім'я клієнта, номер замовлення або сума. Вичищати такий
текст регулярками — програшна гра: **ім'я не має патерну**. Тому обрано інше:

> **Текст помилки не відправляється взагалі.**

Летить тільки:

- **тип** винятку (`KeyError`), ніколи його текст;
- **місце** у трасуванні — файл і рядок, зі шляхами, обрізаними до кореня модуля
  (`adealer/models/document_chain.py:88`), щоб домашня тека розробника теж не
  подорожувала;
- версії та код HTTP-статусу, якщо він був;
- те, що користувач сам напише в полі коментаря.

Неможливо злити VIN через поле, у якому буває лише назва класу. Безпека тут
**структурна**, а не фільтр, за яким треба встигати.

## Що в 3A-dealer ІНАКШЕ, ніж деінде

У більшості модулів будь-який виняток — це справжня поломка. **Тут не так.**
Більшість винятків — `UserError` / `ValidationError`: не заповнили VIN, продали
авто, якого нема на складі, закрили замовлення без механіка. Це модуль
**розмовляє з користувачем**, а не ламається.

Звітувати про них не можна з двох причин одразу:

1. **Шум.** Сотні «помилок» на добу, серед яких справжній баг не видно.
2. **Витік.** Саме в цих повідомленнях і живуть дані: ім'я клієнта, VIN, номер
   замовлення, сума.

Тому в коді є явний список класів, які **не звітуються ніколи**:

```python
EXPECTED_EXCEPTIONS = (
    UserError, ValidationError, AccessError, MissingError, RedirectWarning,
)
```

Звітуються лише **несподівані** винятки: `KeyError`, `AttributeError`,
`TypeError`, помилки HTTP до зовнішніх сервісів тощо.

## Точка підключення — одна

У модулі немає єдиного методу, через який проходять усі збої. Тому таку точку
створено свідомо: декоратор `report_errors('операція')`, який навішується на
входи, де реально ламається, і **більше ніде**:

- імпорти (партнери, адреси, авто, моделі авто; майстри імпорту);
- перевірка й застосування оновлень (`app_update` — ходить по HTTP назовні);
- ланцюг документів (`document_chain` — Рахунок / Видаткова / Акт, видача ЗЧ,
  автопроведення наряду);
- усі крони.

Один декоратор, одна реалізація, яку всі гукають. Не розсипати `try/except` по
двадцяти місцях — розійдуться, і половину забудуть.

```python
@report_errors('chain_create_delivery_note')
def action_create_vydatkova(self):
    ...
```

Декоратор перехоплює виняток, пропускає «розмову з користувачем» без сліду, а
несподіваний — ставить у чергу (як назву класу й рядок коду) і **перекидає далі**.
Для користувача поведінка не змінюється нічим. Якщо навіть постановка звіту в
чергу впаде — оригінальна помилка все одно перемагає.

## Гарантії й чим вони тримаються

| Гарантія | Чим тримається |
|---|---|
| Без явної згоди не йде нічого | `_reporting_enabled()`; «не питали» = «ні» |
| Розмова з користувачем не звітується | `EXPECTED_EXCEPTIONS` у декораторі |
| Текст помилки не передається | `_build_vals` бере лише `exc_type.__name__` |
| Шляхи не викривають файлову систему | `_short_path()` ріже до кореня модуля |
| Користувач бачить, що саме летить | поле `payload` — це сам запит, не переказ |
| Баг у циклі не стає тисячею звітів | `UNIQUE(fingerprint, company_id)` + лічильник + стеля на добу |
| Збій приймача не вішає роботу | відправка окремим `ir.cron`, не в момент падіння |
| Звіт переживає відкат транзакції | окремий курсор |

Усе це перевіряється тестами `adealer/tests/test_error_report.py` (перший набір
тестів у модулі). Ключовий — `test_payload_carries_no_customer_data`: він кидає
помилку, у текст якої навмисно напхано VIN, номер, ім'я клієнта й суму, і
перевіряє, що жодного з них немає у вихідному JSON. **Якщо колись захочеться
додати у звіт текст помилки — саме цей тест має впасти.** Не прибирати.

## Згода та де дивитися чергу

- Увімкнути/вимкнути: **Налаштування → 3A-dealer → Error reports** (типово Off).
  Три стани: увімкнено / вимкнено / «не питали» — останнє рахується як «ні».
- Черга: **Settings → Error reports** (пункт меню). Кожен звіт можна відкрити,
  прочитати поле «What gets sent» (це сам майбутній запит), доповнити коментарем,
  відправити вручну або видалити.
- Куди йде: налаштовуваний ендпоінт (`Reporting endpoint`). Політика забороняє
  вихідні виклики назовні — вкажіть свій колектор.

## Що йде у звіті

```json
{
  "schema": 1,
  "install_id": "11b38316...",
  "odoo_version": "19.0",
  "module": "adealer",
  "module_version": "19.0.1.7.0",
  "operation": "chain_create_delivery_note",
  "error_type": "KeyError",
  "http_status": 0,
  "fingerprint": "4aad1a2263c2a68c",
  "occurrences": 1,
  "frames": ["adealer/models/document_chain.py:88 in _build_chain_move"],
  "comment": ""
}
```

`install_id` — випадкове число, створюється при постановці першого звіту в чергу.
Воно відрізняє «один інстанс падає 50 разів» від «50 інстансів впали по разу», але
нічого не каже про власника бази.
